# Troubleshooting

Start with `sandbox repair`, then `sandbox doctor` and `sandbox logs -f`.

## What doctor checks and repair can fix

`sandbox doctor` and `sandbox repair` run the same checks, grouped under headings, one line each as it finishes. A line that is not fine says what it means and what to do. A check that takes more than 20 seconds (a stuck Windows tool, no network) is skipped with "took too long" and the rest go on.

- `sandbox doctor` only looks. When some problems can be fixed it asks "N problems can be fixed. Fix them now?" (`--fix` does it without asking; without a terminal it only tells you).
- `sandbox repair` lists exactly what it will change, asks once (`--yes` skips the question), makes the changes, looks again to see they worked and prints "fixed", "needs you" or "still not right" for each. The log of what it found and changed (before and after) is `<storage>\logs\repair-<time>.log`; its path is printed at the end. Repair never deletes your settings, logins, history or projects: it removes leftovers and links the sandbox made, and moves pointers back.
- `--json` for both prints the results (`id`, `group`, `status`, `detail`, `fixable`, and after a fix what changed). With `--json`, repair changes nothing unless you add `--yes`.
- Menu: Maintenance > Health > "Run the checks and fix what can be fixed" runs `sandbox repair` on the normal screen.

| "claude-mem save failed: ENOENT" | Fixed: files the agent removes during a save are skipped, and SQLite `-journal` files are never copied |

## The PC froze or restarted during heavy builds

If the whole PC stops responding (not only the sandbox window closing) and Windows restarts, check these in order:

1. **vGPU.** With `sandbox.vGpu` on (also when a project's `.sandbox-config.json` turned it on, which only works if your own settings or your answer allow it), the sandbox uses this PC's graphics card. With some graphics drivers, heavy use can freeze the whole PC: a hard freeze with Kernel-Power 41 and no file in `C:\Windows\Minidump` is typical of a graphics driver hang. Turn it off (`sandbox config set sandbox.vGpu false`) unless a program in the sandbox needs the GPU; the mesa toolchain gives software OpenGL without it. The tool never turns it off for you. While it is on, the tool runs the sandbox *gentler* by itself (see below), and `sandbox launch` and `sandbox doctor` say so.
2. **`sandbox logs --crash`** prints the report of the last crash: when this PC was last seen working and when it restarted ("This PC stopped responding at ... and was restarted at ... (n minutes later)"), the Windows events that matter, what each usually means, any crash dump, and this PC's memory during the run (`<storage>\logs\host-memory-<data>.log`, a line a minute, every 10 seconds while the PC was low).
3. **Event Viewer** (Windows Logs > System, or Applications and Services Logs > Microsoft > Windows > Hyper-V-Worker and Hyper-V-Compute):
   - `Kernel-Power 41` is the unexpected restart itself; its BugcheckCode is 0 for a freeze, a power cut or a held power button, and the stop code of a blue screen otherwise.
   - `BugCheck 1001` (source WER-SystemErrorReporting) names the stop code of a blue screen.
   - `WHEA-Logger 17, 18, 19, 47` are hardware errors Windows saw (CPU, memory, bus, disk): heat or failing hardware, not something a sandbox setting fixes.
   - `Resource-Exhaustion-Detector 2004` says this PC ran out of memory (RAM plus paging file) and names the biggest users.
   - `C:\Windows\Minidump` (and `C:\Windows\MEMORY.DMP`) hold the crash dump of a blue screen; the report lists only their names and times.
4. **Memory.** See the next section: a sandbox takes its memory from this PC as it goes.

## The sandbox closes under heavy load

Windows Sandbox's memory setting (`sandbox.memoryMb`) is a ceiling, not a reservation: the virtual machine's memory is taken from this PC on demand (it shows as `vmmem`). What decides whether heavy parallel builds slow down or the sandbox is closed (or the PC locks up) is therefore this PC's *commit limit*, its RAM plus paging file, not only the sandbox's own size. These protections are on by default and need no setting; they make heavy load slow things down instead of closing the sandbox:

| Protection | What it does | Default |
| --- | --- | --- |
| Memory sizing | `memoryMb: "auto"` gives the sandbox at most the free RAM **and** the PC's unused commit (HostTools `memory-status`) minus `reserveHostMb`. Whatever is asked, it never gets more than this PC can keep in RAM for it: the PC's RAM minus max(`reserveHostMb`, 25 %), and 2 GB more with vGPU (a fixed `memoryMb` above that is lowered, and the launch says so). Memory beyond that would be paged to this PC's disk while the sandbox pages to its own, which is what can freeze a whole PC. When the commit made the size much smaller than free RAM allowed, the launch says so too | on |
| Last-resort backstop | Everything the agents start (their builds, tests, tools; not the boot, the daemon or ptyhost) shares one Windows job object. Its only limit sits just below the sandbox's commit limit (`sandbox.agentMemoryHeadroomMb`, `"auto"` = the larger of 1.5 GB and 3 %), set once when the job is made. It can only matter when Windows inside the sandbox is about to refuse memory to everyone: then a build is refused instead of Windows. Slowing down (below) comes long before | on |
| Governor in the sandbox | Every 2 seconds the daemon looks at the sandbox's memory and turns a dial, like a PC that gets slower instead of failing. Step 1 (below 15 % free RAM or above 80 % commit): compilers, linkers and build tools (rustc, cc1, link, lld, clang, cl, dotnet, msbuild, ninja, make, cmake ...) run at lower CPU priority and low memory priority, so Windows moves their pages to the paging file before the agents'. Step 2 (10 % / 88 %): idle priority, the compilers share at most 60 % of the CPU, and only some of them run at a time: the others wait their turn (suspended a few seconds at a time, always resumed, never killed), and who waits changes every 20 seconds. Step 3 (6 % / 94 %, or commit that would run out within 20 seconds at its current rate): 35 % CPU, a third of the compilers at a time, the waiting ones trimmed to the paging file. Step 4 (4 % / 97 %, or 8 seconds): 15 % CPU, one compiler at a time. It turns up at once and down one step after three calm samples. Builds get slower; nothing fails. Agents (claude, codex, gemini ... also when they run as node), shells, ptyhost and Windows are never touched. What it did is in the memory log (`C:\AgentData\logs\memory-*.log`, lines starting `governor:`) and `run\pressure.json` | on (`sandbox.pressureResponse`) |
| Watchdog on this PC | The background sync samples this PC every 10 seconds. When available RAM is below max(4 GB, 12 %), or available commit below 15 % (or half of `reserveHostMb`), or the CPU stays above 95 % for 60 seconds, or the disks' queue length stays at 32 or more for 40 seconds (heavy builds writing through mapped folders; skipped when the PC has no such counter), it asks the sandbox to slow its builds down: the governor goes to at least step 2 (repeated every 30 seconds while it lasts; the same thresholds with 25 % margin to end). When this PC is nearly out of memory (under 1.5 GB of RAM free, or commit within max(2 GB, 4 %) of its limit) the request says so at once and builds go to step 4 until it passes. It logs this in `host-sync-<data>.log` and never blocks | on |
| Build budget | Programs in a sandbox see the sandbox's maximum (every processor, all its RAM). The tool gives them what they may really use: with a CPU cap, the sandbox's programs run on that share of the processors (so cargo, .NET, ninja and `nproc` count right) and `NUMBER_OF_PROCESSORS` says the same; each agent session gets `CARGO_BUILD_JOBS` and `CMAKE_BUILD_PARALLEL_LEVEL` (when not set already) from a budget of one job per 3 GB after 6 GB, at most 8 per session and shared with the sessions already building; links at once follow the same rule (2 to 8). `run\budget.json` (path in `SANDBOX_BUDGET_FILE`) holds these numbers for agents to plan with. The governor is the brake beyond that | on |
| Gentler with vGPU | With vGPU on: the sandbox's CPU cap is 15 points lower (at least 50 %), every step of the governor starts earlier (step 1 at 20 % free RAM or 75 % commit), the watchdog below max(6 GB, 15 %) free RAM or 20 % commit, 90 % CPU for 45 seconds or a disk queue of 16 for 30 seconds, compilers run below normal priority from the start, and at most max(2, cores / 4) heavy compilers (rustc, clippy-driver, link, lld, clang, cl ...) run at once: the newer ones wait, paused a few seconds at a time and never killed | automatic |

Settings (all yours only; a project's `.sandbox-config.json` cannot change them): `sandbox.agentMemoryHeadroomMb` (`"auto"`, a number of MB, or `"none"` for no backstop), `sandbox.pressureResponse` (`false` turns the governor off), `sandbox.reserveHostMb`, `sandbox.maxMemoryMb`, `sandbox.memoryMb`.

`sandbox doctor` ("This PC", "Memory for the sandbox") reads this PC's paging file setup. If it is fixed or off and too small for the sandbox plus what this PC uses now, it warns: Windows Sandbox takes its memory as it goes, and if this PC runs out, Windows closes the sandbox instead of slowing it down. The fix is yours to make: let Windows manage the page file (System > Advanced system settings > Performance > Settings > Advanced > Virtual memory: "Automatically manage paging file size"), or make it at least the size doctor names. The same hint is printed at launch, once a day at most. Nothing changes the page file for you.

If it still closes: `sandbox logs --crash` and the memory log (`C:\AgentData\logs\memory-*.log`, last lines before the end) show what used the memory.

## Contained storage (Beta)

For `storage.contained: "vhdx"` ([configuration](configuration.md#contained-storage-beta)). **Beta, not yet tried on a real PC**: if something here goes wrong, `sandbox storage contained off` is the way back, and `sandbox doctor` says what it sees.

| Problem | What to do |
|---|---|
| "Contained storage is still mounted from an earlier sandbox" (a line at the start of a command), or doctor says "the image is still mounted ... and nothing uses it" | A sandbox ended (or crashed) without dismounting. `sandbox repair` dismounts it (Windows asks for permission). The image and everything in it are fine. By hand: in an admin terminal run `diskpart`, then `select vdisk file="<storage>\images\<name>.vhdx"` and `detach vdisk` |
| Doctor says "the record says the image is mounted, but it is not" | Only the bookkeeping file `<storage>\mounts\state.json` is out of date. `sandbox repair` corrects it; nothing is mounted or dismounted |
| "The image is still attached (something is using it)" / "the image is in use" when dismounting | A program has a file open in the image (Explorer or a terminal in `<storage>\mounts\<name>`, a scanner, an editor). Close it and run `sandbox repair` again. The sandbox must be closed too: a dismount is refused while Windows Sandbox runs |
| "The image is attached somewhere else" | It was attached with Disk Management or another tool (maybe with a drive letter). Detach it there (or with the diskpart commands above), then start again |
| Windows did not give permission (the prompt was declined or closed) | The mount and the dismount each need one Windows permission prompt. Run the command again and choose Yes. A launch cannot start without it; turn the feature off with `sandbox storage contained off` if you do not want the prompts |
| "The mount folder is not empty" / "is a mount point already" | Something is in `<storage>\mounts\<name>` that this tool did not put there, or another disk is mounted there. Nothing is changed: look at the folder, remove what does not belong (when it is a mount point, detach that disk), then try again |
| "The image is missing" | The `.vhdx` file under `<storage>\images` was moved or deleted. Put it back, or `sandbox storage contained off` and then `on` for a new empty image (tools are downloaded again) |
| "The image is bigger than the limit" / "differencing disk" / "not yours" | The script refuses images it did not make: a larger size than `storage.containedMaxGb`, one that depends on a parent file, or one owned by another user. Nothing is changed. Raise `containedMaxGb`, or use the image you made |
| "Someone else may change ..." (the storage helper) | The storage helper only mounts folders and images that nobody but you, SYSTEM and administrators may change. `sandbox repair` makes the images and mounts folders private; for the storage folder itself, remove the extra permission (Properties > Security) or move your storage (`sandbox storage move`) |
| "Not yours (owner ...)" from the storage helper | A folder or the image belongs to another account, often Administrators because it was made from an admin terminal. Take ownership back (Properties > Security > Advanced > Owner) or make a new image (`sandbox storage contained off`, then `on`) |
| "The storage helper used other folders ..." | The helper reads your settings from `%USERPROFILE%\.agent-sandbox\config.json` and the machine file; this command used other ones. Run without `--config`, or put the storage folder in your usual settings |
| "The image was not closed cleanly ... permission prompt" | The PC lost power while the image was mounted. The helper does not replay the disk's log; the permission prompt (which runs the scripts) does it once, after which the helper works again |
| "Too many calls; wait a minute" / "Only members of the Agent Sandbox Users group" | The helper answers 10 calls a minute per user. Membership counts after signing out and in. Without membership the permission prompt is used |
| A file `main.vhdx.failed-<time>` appears in `images` | The first creation did not finish; the unfinished image was renamed, never deleted. It holds nothing of yours: delete it when you like |
| "Contained storage cannot be used: ... inside a Windows Sandbox" | Disk images cannot be mounted in a sandbox. Run the command on your PC |
| `sandbox storage move` says the contained storage is mounted | Dismount first (`sandbox repair`, or close the sandbox and wait for the watcher to let go). A move would otherwise copy into the image |
| `sandbox data` shows little or nothing after turning it on | It still reads the plain data folder; the tools, state and logs are in the image. Look inside while it is mounted, or turn it off to get them back as folders |
